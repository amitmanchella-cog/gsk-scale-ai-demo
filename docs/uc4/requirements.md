## 1. Goal and users

A field rep can build a prioritised weekly call plan for their territory in **under 5 minutes**. Two personas use
the same screen: the **field rep** (plans their own week) and the **district manager** (selects any rep to review
that rep's plan — no auth/SSO is in scope, so "selecting a rep" is the persona switch).

## 2. Scope

**In scope** — the three PRD features, split into five user stories below (S1–S5). S4 and S5 carry the parts of the
PRD that are not a user-visible feature by themselves (CSV export, packaging and non-functional requirements) so that
every piece of work has exactly one owner, one Jira sub-task and one child build session.

**Out of scope** (verbatim from the PRD): CRM integration (e.g. Veeva), real HCP data or PII, SSO, mobile app, route
optimisation, GenAI features. Also out of scope for this ticket: persisting plans across server restarts (plans are
held in memory per rep), multi-week planning, editing the scoring rules from the UI (rules are configuration).

## 3. Data and definitions

All data comes from the UC1 curated tables; no new data is generated. Facts used below were measured on the repo data
(`data/*.parquet`, generated by `data/generate.py`, seed 42):

| Term | Definition |
|---|---|
| Territory of a rep | `reps.territory_id`. 30 reps across 20 territories (10 territories have 2 reps). "The rep's HCPs" are all `hcps` rows with that `territory_id` (59–101 per territory, 1,600 total). |
| As-of date | The date "today" is measured from. Visits span 2025-04-01 → 2025-09-29, so the default as-of date is the **latest `visit_date` in the loaded data (2025-09-29, a Monday)**, overridable with `NAVIGATOR_AS_OF_DATE` or `?as_of=YYYY-MM-DD`. Using the wall-clock date would put every HCP >1 year overdue and make the demo meaningless. |
| Days since last visit | `as_of − max(visits.visit_date)` for that HCP, in whole days. 155 HCPs have never been visited: `days_since_last_visit = null`, treated as "maximum" for scoring and filtering, and shown as "never visited". |
| Open follow-up | A `follow_ups` row for that HCP with `status == 'open'` (470 HCPs have ≥1). |
| Planning week | Mon–Fri starting on the as-of date's Monday. Slots are per day; there is no time-of-day. |
| Overdue Segment A | `segment == 'A'` and (`days_since_last_visit > 30` or never visited). |

## 4. User stories and acceptance criteria

Acceptance criteria are numbered **AC1–AC6 exactly as in the PRD**; additional criteria needed to make a story
testable are numbered `Sx.y`. Every criterion is traced to a test in §6.

### S1 — Territory HCP list (`AC1`)

*As a field rep, I want to see the HCPs in my territory with filters and search, so that I can find who to visit
without a spreadsheet.*

- **AC1** — Given a rep is selected, when the HCP list opens, then only HCPs in that rep's territory appear, and the
  filters and search narrow the list correctly.
- **S1.1** — Given the rep selector, when the page loads, then all 30 reps are listed as `rep_name (rep_id, territory)`
  and none is selected until the user picks one (the list is empty with a prompt until then).
- **S1.2** — Given a selected rep, when the list renders, then each row shows `hcp_id`, `hcp_name`, `specialty`,
  `segment`, days since last visit (or "never visited"), open follow-up count, **score** and **reason** (from S2),
  sorted by score descending then `hcp_name`.
- **S1.3** — Given the filters, when the user sets specialty (one of the 6 values or "All"), segment (A/B/C/All) or
  "days since last visit ≥ N", then the list shows only rows matching **all** active filters; "never visited" rows
  match any N.
- **S1.4** — Given the search box, when the user types text, then rows are kept whose `hcp_name` contains the text
  case-insensitively; search combines with filters (AND).
- **S1.5** — Given the API, when `GET /reps/{rep_id}/hcps` is called for an unknown rep, then it returns `404`.

### S2 — Visit priority score (`AC2`, `AC3`)

*As a field rep, I want every HCP scored 0–100 with a plain-language reason, so that I know who to prioritise and
why.*

Scoring rules (defaults, configurable — see S2.3):

| Rule | Default |
|---|---|
| Segment weight | A = 40, B = 25, C = 10 |
| Days since last visit | +1 per day, capped at 40; never visited counts as the cap |
| Open follow-up | +20 if the HCP has ≥ 1 open follow-up (flat, not per follow-up) |
| Visited in the last 7 days | score = 0 (`days_since_last_visit ≤ 7`), reason states this |
| Total | sum of the above, capped at 100 |

- **AC2** — Given an HCP is Segment A, 45 days since last visit, with 1 open follow-up, when its score is calculated,
  then the score is 100 (40 + 40 cap + 20, capped at 100) and the reason text lists all 3 factors, e.g.
  `"Segment A (+40), 45 days since last visit (+40, capped), 1 open follow-up (+20)"`.
- **AC3** — Given an HCP was visited 3 days ago, when its score is calculated, then the score is 0 and the reason is
  `"Visited 3 days ago (within 7 days)"`.
- **S2.1** — Given an HCP that has never been visited, when scored, then the days component is the cap (40) and the
  reason says "never visited".
- **S2.2** — Given a Segment C HCP visited 12 days ago with no open follow-up, when scored, then the score is 22
  (10 + 12) and the reason lists exactly 2 factors (no "+0" factors are printed).
- **S2.3** — Given the scoring rules, when they are changed through configuration (`NAVIGATOR_SCORING_RULES` JSON
  or `scoring_rules.json`), then scores use the new values without code changes, and `GET /scoring/rules` returns the
  rules in effect.
- **S2.4** — Given the scoring module, when the unit tests run with coverage, then `app/scoring.py` has ≥ 90% line
  coverage (enforced in CI with `--cov-fail-under=90` scoped to that module).

### S3 — Weekly plan builder (`AC4`, `AC5`)

*As a field rep, I want to place HCPs into Mon–Fri slots with a cap of 6 per day and be warned about gaps, so that
my week is realistic and covers the right HCPs.*

- **AC4** — Given a day already has 6 visits, when the rep adds a 7th, then the add is blocked with a message
  (API: `409 {"detail": "Tuesday already has 6 visits (max 6)"}`; UI: inline message, the plan is unchanged).
- **AC5** — Given a Segment A HCP is more than 30 days overdue and not in the plan, when the rep views the plan,
  then a warning names that HCP (one warning per HCP, e.g. `"Dr Isla Xu (Segment A) is 51 days overdue and not
  planned"`; the warning disappears once the HCP is added to any day).
- **S3.1** — Given the plan, when the rep adds an HCP who is already planned on another (or the same) day, then the
  add succeeds and a **duplicate warning** names the HCP and both days (warn, don't block — a second visit may be
  intentional).
- **S3.2** — Given a planned visit, when the rep removes it, then it disappears from the day and the warnings are
  recomputed.
- **S3.3** — Given a selected rep, when the plan is loaded, then it contains that rep's plan only (plans are keyed by
  `rep_id`, in memory for the life of the server process) and each day shows `n/6` visits.
- **S3.4** — Given an HCP from another territory, when it is added to this rep's plan via the API, then the add is
  rejected with `422`.

### S4 — Plan CSV export (`AC6`)

*As a field rep, I want to download my plan as CSV, so that I can take it into the tools I already use.*

- **AC6** — Given a completed plan, when the rep exports it, then a CSV downloads with day, HCP, specialty, score and
  reason. Exact header: `day,hcp_id,hcp_name,specialty,segment,score,reason`; one row per planned visit, ordered
  Mon→Fri then by score descending; filename `plan_<rep_id>_<week_monday>.csv`; `Content-Type: text/csv`.
- **S4.1** — Given a reason containing commas (they do — see AC2), when exported, then the field is RFC 4180-quoted
  and round-trips through `csv.reader`.
- **S4.2** — Given an empty plan, when exported, then the CSV contains the header row only (no error).

### S5 — Packaging, CI gates and non-functional requirements

*As the tech lead, I want the app to ship as a container with CI gates, so that UC3 can run it and every PR proves
lint, tests, coverage and build.*

- **S5.1** — Given `apps/navigator/Dockerfile`, when built, then one image serves the API and the built frontend on
  port 8000 (`/` → SPA, `/api/*` → FastAPI, `/health` → ok) with the curated tables baked in.
- **S5.2** — Given a PR, when CI runs, then it executes ruff, backend pytest (with the S2.4 coverage gate), frontend
  lint/test/build **and** the container build (`docker build`), and all must pass.
- **S5.3 (performance)** — Given a territory of 300 HCPs, when `GET /reps/{rep_id}/hcps` is called, then it responds
  in < 1 s (measured in a backend test against a synthetic 300-HCP fixture; p95 of 5 calls).
- **S5.4 (accessibility)** — Given keyboard-only use, when the user tabs through the page, then the rep selector,
  filters, search, every "Add to <day>" control, every "Remove" control and "Export CSV" are reachable and operable
  with Tab/Enter/Space, have visible focus and accessible names; warnings are announced via `role="alert"`/`aria-live`.
- **S5.5** — Given the repo README and `apps/navigator/README.md`, when a new engineer follows them, then they can run
  the app locally (backend + frontend or the container) and the tests.

## 8. Assumptions and open questions

1. **As-of date** defaults to the latest visit date in the data (2025-09-29) so "days since last visit" is meaningful
   on the frozen synthetic dataset. Confirm or supply a different default.
2. **Open follow-up bonus is flat (+20)** regardless of how many follow-ups are open; the reason shows the count.
3. **Duplicates warn, the day cap blocks** — the PRD says "warns about duplicates" and "at most 6 visits a day", read
   as warn vs. block respectively.
4. **Plans are in-memory per rep** for this ticket (no database); a restart clears them. Persistence would be a
   follow-up ticket.
5. **District manager** has no separate screen: they pick a rep from the same selector. A read-only manager view is
   not required by any AC.
6. **Scoring rules are configuration, not UI** — editable via `NAVIGATOR_SCORING_RULES` / `scoring_rules.json`.
